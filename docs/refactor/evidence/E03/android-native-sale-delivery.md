# Android native sale delivery

Android commit `0b20e2c` reserves an eligible sale for one cloud command using the original invoice, line, payment and stock movement UUIDs. SQLite saves the command with the invoice acceptance. Retry uses the same checkout attempt key and body. The original financial rows stay reserved until cloud acknowledgement.

- Android emulator `5556` used the local Docker TLS API with a disposable paid shop and an owned device. The test dropped the first response after the API committed, reopened SQLite, and replayed the original key and body. The server and device retained the original invoice, line, payment, and movement IDs. Stock stayed at 9 after a single sale from 10, including after an additional sync. The pull cursor stayed at its previous position while the row was reserved and then advanced after acknowledgement. The disposable shop, account, and mail were removed.
- The opt-in Flutter suite passed 53 tests. Coverage includes retry after loss, unsupported server or device behavior, legacy row isolation, rejection, mismatched acknowledgement, account-bound HTTP retry, and edits before or during delivery. Flutter analysis passed. The full default-build suite passed 562 tests with 22 skips, including the opt-in-only cases.
- Docker passed 11 focused tests across capabilities, atomic sale posting, and the shared sync fixture, then all 428 API integration tests. The full suite reported the existing duplicate health operation ID warning. Web typecheck and generated type verification passed for both capability changes. Commits `1980c70` and `ace0ac5` add server negotiation. Web commits `1de7fe7` and `7910d2a` record the generated contract.

The flag defaults to off. Release enablement needs historical snapshot fidelity checks for cost, HSN, and units, explicit reconciliation of shortages and local edits, and a mixed-version upgrade and restore strategy. Later payments, cancellations, and credit notes have their own atomic delivery gates.
