# Storely: Own-Server Migration Plan

> Last updated 2026-10-25. Status: **Phases 0-3 done; Phase 4 (Flutter app on the new backend) next (awaiting go-ahead).**
> Per CLAUDE.md, each phase starts only after the user confirms it.
> Principle: **security first.** Every phase has a security gate (section 6).

## 1. Goal

Move Storely off Supabase onto a backend we own and run, and add a desktop web
app for shop owners **and their staff**.

1. **API server** (Python, FastAPI, PostgreSQL) that replaces Supabase: auth,
   shops and members, device registration, sync, and report/export endpoints.
2. **Web app** (React) for computers. Cloud-only. Priorities, in order:
   **Products and Reports first, Billing second.**
3. **Flutter app stays.** It keeps working fully offline (local SQLite, no
   account needed, "Start Fresh"). Cloud sync becomes optional and points at
   our API instead of Supabase.
4. **Everything runs locally in Docker first.** Hosting is decided later.

## 3. Decisions

**Confirmed by the user**
- Backend is Python with FastAPI. Web is React.
- The existing Flutter app is kept and is not rewritten.
- Local-only mode stays: a solo user needs no server.
- The web app is cloud-only. **Staff can use the web app too** (not only owners
  and admins).
- Own server replaces Supabase fully.
- **Security first.** All data is encrypted in transit, and the full set of
  security and auth features in section 5 is in scope, not a later add-on.
- **Login is email + password only for now** (no phone OTP).
- **No real data exists in Supabase.** No data migration; we start clean.
- **Start with local development in Docker**, so it runs the same anywhere.
  Hosting, domains and the production email provider are deferred.

**Recommended (change if you disagree)**

| Area | Choice | Why |
|---|---|---|
| Database | PostgreSQL 18, same schema as today | Keeps tables, triggers and server-clock sync logic. Portable to any host. |
| DB access | SQLAlchemy 2 (async) + asyncpg, Alembic migrations, Pydantic v2 | Standard, typed, well supported. |
| Passwords | argon2id | Current best practice. |
| Tokens | Short-lived signed JWT access token + rotating opaque refresh token | Fast checks, revocable sessions (see 5.2). |
| Authorization | Role checks in FastAPI **and** Postgres RLS kept as a safety net (4.2) | Two layers; avoids rewriting 62 policies. |
| Money | `NUMERIC` in Postgres, `Decimal` in Python. Never float on the server. | Billing app; matches the CLAUDE.md money rule. |
| Reports | SQL in Postgres, shaped in Python, Excel via `openpyxl` | The reports are aggregations, not heavy compute. |
| API contract | OpenAPI generated by FastAPI; TypeScript client generated from it | One source of truth; web cannot drift. |
| Web | Vite, React Router, TanStack Query + Table, Tailwind + shadcn/ui, Recharts | Common, fast, good for data-heavy admin screens. |
| Rate limiting | Counters in Postgres at first (no extra service) | Fewer moving parts to secure; add Redis only if load needs it. |
| Email codes | 6-digit codes for verification and password reset, entered in the app | Works the same in the mobile app and the web, no deep links. |
| Background jobs | FastAPI background tasks first; add a queue only when exports get slow | Do not build infrastructure before it is needed. |

## 4. Target architecture

```
 Flutter app (Android)                 React web (computer)
 SQLite = source on device             cloud-only, no local DB
        |  HTTPS: sync (pull/push)            |  HTTPS: REST (read + domain writes)
        +------------------+------------------+
                           v
              Caddy / reverse proxy  (TLS 1.2+, HSTS)
                           v   TLS
                  FastAPI  (storelyapi)
         auth . shops/members . devices . sync . reports
                           v   TLS (verify-full)
                  PostgreSQL 18 (+ encrypted backups)
```

### 4.1 What Supabase does today and what replaces it

| Today (Supabase) | Replacement in `storelyapi` |
|---|---|
| `auth.signInWithPassword / signUp / signOut` | `POST /v1/auth/login`, `/signup`, `/logout`, `/refresh` |
| `auth.users` + `profiles` + `handle_new_user` trigger | Own `users` table; signup creates the profile row |
| RPC `create_shop` | `POST /v1/shops` |
| RPC `my_pending_invite_shop`, `accept_invite` | `GET /v1/invites/pending`, `POST /v1/invites/accept` |
| RPC `register_device` (per-install bill letter) | `POST /v1/devices/register` |
| RPC `sync_pull` | `POST /v1/sync/pull` (same keyset paging) |
| RPC `is_shop_admin`, `get_shop_role` | `GET /v1/shops/{id}/role` |
| Table upserts via PostgREST | `POST /v1/sync/push` |
| 62 RLS policies, 17 SQL functions, 6 triggers | Ported to the new schema (see 4.2) |
| Edge cases tested in `supabase/tests/*.sql` | Same SQL tests re-run, plus pytest API tests |

The app uses no Supabase realtime or storage, so nothing else needs replacing.

### 4.2 Authorization: two layers

1. FastAPI checks the caller's role on every request (owner, admin, staff).
   The role is read from the database on each request, never trusted from the
   token, so removing a member or changing a role takes effect immediately.
2. Each request runs in one transaction that first sets
   `SET LOCAL app.user_id = '<uuid>'`. A small SQL function `app.uid()`
   replaces `auth.uid()`, so the existing RLS policies keep working as a second
   line of defense. The app connects as a normal role that does not bypass RLS.

### 4.3 Sync stays table-based

Keep the current protocol so the Flutter sync engine barely changes:

- Every row carries `server_updated_at`, stamped by the existing trigger
  (`storely_sync_before_write`), including the "deleted bills stay deleted" and
  last-write-wins rules.
- Pull is keyset-paged by `(server_updated_at, key)`, as `sync_pull` does now.
- Push is a batch upsert per table; a refused row returns a per-row error that
  the app maps to `SyncRowRejected`, as today.
- Synced tables: `shops, app_settings, bill_settings, categories, units,
  suppliers, customers, products, invoice_series, bills, bill_items,
  bill_payments, stock_movements`. Expenses and `audit_log` follow the same rule
  as the engine already handles them.
- Pushes are idempotent (same row twice has the same result), so a retry after
  a dropped connection never duplicates anything.

### 4.4 Web does not use raw table sync

The web has no local database, so it uses normal REST:

- **Reads:** paged, searchable list endpoints (products, customers, bills,
  suppliers) and report endpoints.
- **Writes:** domain endpoints (create product, adjust stock, create bill) that
  write the same rows inside one transaction, so phones pick them up on the next
  pull. Bill creation takes an idempotency key.
- The web registers as a device (own bill-number letter), so invoice numbers
  never collide with phones.
- **Billing logic exists once more on the server.** Totals, GST split, round-off
  and invoice numbering must match `BillTotals` and `InvoiceNumbering` in the
  Flutter app. The server is authoritative for bills made on the web, and shared
  test vectors keep both implementations equal (Phase 8).

### 4.5 Roles on the web (proposed, please confirm)

Rules follow what the app enforces today (admin-managed tables, admin-only
cancel). The server filters fields too, so staff never receive data they may
not see.

| Capability | Owner | Admin | Staff |
|---|---|---|---|
| Create bills, record payments | yes | yes | yes |
| View products and stock | yes | yes | yes (no cost/purchase price) |
| Add/edit/delete products, adjust stock, import | yes | yes | no |
| View customers and dues | yes | yes | yes |
| Cancel bills, credit notes | yes | yes | no |
| Reports (day book, P&L, ageing, valuation, tax, GSTR-1) | yes | yes | no |
| Export data | yes | yes | no |
| Manage staff and invites | yes | yes (staff only) | no |
| Manage admins, transfer ownership, delete shop | yes | no | no |
| Shop settings | yes | yes | no |
| View security events for the shop | yes | yes | no |

## 5. Security requirements

These are requirements, not nice-to-haves. A phase is not done until its
security gate (section 6) passes.

### 5.1 Encryption in transit (everything, every hop)

- TLS 1.2 minimum, TLS 1.3 preferred, modern cipher suites only. No plain HTTP
  anywhere except a redirect to HTTPS. HSTS with a long max-age.
- **App/web to API:** HTTPS only. The Android release build disables cleartext
  traffic. Certificate pinning (with a backup pin) is evaluated in the
  production phase, since a bad pin can lock users out.
- **Proxy to API:** TLS as well, even on the same host.
- **API to PostgreSQL:** TLS with `sslmode=verify-full`.
- **Email:** the API sends mail over TLS (STARTTLS required). The only
  exception is the local-dev mail catcher, which holds fake mail only and is
  documented as dev-only.
- Local development uses TLS too (a local certificate authority, section 7), so
  dev behaves like production.

### 5.2 Authentication and sessions

- **Signup:** email + password. Email must be verified (6-digit code, hashed,
  10-minute expiry, limited attempts) before the account can create or join a
  shop or sync.
- **Password rules:** minimum 10 characters, no silly composition rules, blocked
  if common or in a bundled breached/common-password list, Unicode-normalised,
  maximum 128 characters. Hashed with argon2id and per-user salt.
- **Login protection:** rate limits per IP and per account, progressive delay
  after failures (no permanent lockout, which would be a denial-of-service
  tool), constant-time comparison, and identical responses for unknown email and
  wrong password so accounts cannot be enumerated.
- **Access token:** signed JWT (asymmetric key, key id, rotation), about 10-15
  minutes, with `iss`, `aud`, `sub`, `sid`, `exp`. The role is not in the token.
- **Refresh token:** opaque random 256-bit value, stored only as a hash,
  rotated on every use, with **reuse detection**: if an old token is replayed the
  whole session family is revoked. Absolute session lifetime is enforced.
- **Sessions:** a user can see their active sessions and devices and revoke any
  of them, or log out everywhere. Changing the password revokes all other
  sessions. Removing a member from a shop ends their access immediately.
- **Password reset:** by emailed code, single use, short expiry, hashed in the
  database, rate limited, no account enumeration. A reset revokes all sessions.
- **Password change:** requires the current password.
- **Two-factor authentication:** TOTP (authenticator app) with one-time
  recovery codes. Secrets are stored encrypted. Available to everyone; whether
  it is *required* for owners and admins is an open question (section 9).
- **Notifications:** email on new-device sign-in, password change, 2FA change
  and email change.
- **Security events:** sign-ins (success and failure), password and 2FA changes,
  session revocations, role changes and invites are recorded in an append-only
  table. Owners and admins can view their shop's events; users can see their own.
- **Account lifecycle:** change email (re-verified), delete account, and export
  my data. Deleting an account from inside the app and from a web page is also
  a Google Play requirement for apps that create accounts.

### 5.3 Authorization

- Every endpoint declares the roles it allows; deny by default.
- Role and shop membership are loaded from the database on every request.
- Tenant isolation: a user from shop A can never read or write shop B.
  Resources of other shops return 404, not 403, so IDs cannot be probed.
- RLS stays enabled as a second layer (4.2); the app database role cannot
  bypass it.
- Field-level filtering on the server (staff never receive cost prices, margins
  or admin-only data).

### 5.4 API hardening

- Strict input validation (Pydantic), maximum body sizes, pagination limits,
  request timeouts.
- Parameterised queries only. No string-built SQL.
- Per-endpoint rate limits. Idempotency keys for bill creation and sync pushes.
- CORS allow-list limited to the web origin. CSRF protection on the cookie-based
  refresh endpoint (`SameSite=Strict` plus a required custom header).
- Security headers on all responses and on the web app: CSP, HSTS,
  `X-Content-Type-Options`, `frame-ancestors 'none'`, `Referrer-Policy`,
  `Permissions-Policy`.
- Errors never leak stack traces or internals. Interactive API docs are off or
  login-protected outside development.

### 5.5 Data protection

- Passwords: argon2id hashes only. Reset codes, refresh tokens and recovery
  codes: stored hashed. TOTP secrets: encrypted with AES-256-GCM using a key
  from the environment.
- Secrets live in environment variables or Docker secrets, never in git, and
  are never logged. Logs redact passwords, tokens, codes and personal data.
- At rest: database disk encryption is a hosting-time decision; backups are
  always encrypted. Collect the minimum personal data.
- The phone's local SQLite is unencrypted today; optional database encryption
  is listed under "Later" because of its performance and recovery trade-offs.

### 5.6 Containers and supply chain

- Containers run as non-root with a read-only filesystem, dropped capabilities,
  `no-new-privileges`, and small pinned base images.
- Dependencies are pinned with lockfiles. CI runs `pip-audit`, `npm audit`,
  an image scan (Trivy) and secret scanning (gitleaks, also as a pre-commit hook).
- Static analysis: `bandit` for Python (`semgrep` in Phase 9), oxlint security rules for
  the web.

### 5.7 Mobile and web clients

- **Flutter:** tokens kept in Android Keystore-backed secure storage
  (`flutter_secure_storage`, a new dependency to confirm in Phase 4). The
  existing app lock stays. Release builds refuse cleartext HTTP.
- **Web:** access token in memory only; refresh token in an `httpOnly`,
  `Secure`, `SameSite=Strict` cookie; nothing sensitive in `localStorage`, URLs
  or logs. Strict CSP, no inline scripts.

### 5.8 Security testing (built in, not at the end)

- A short **threat model** (STRIDE) written in Phase 0 and updated each phase.
- An **authorization matrix test**: every endpoint x every role x own shop and
  other shop.
- Token tests: expired, tampered, wrong algorithm, wrong audience, replayed
  refresh token.
- Brute-force and rate-limit tests; enumeration tests (identical responses).
- API fuzzing from the OpenAPI schema (Schemathesis).
- OWASP ZAP baseline scan against the local stack in CI; `testssl.sh` check of
  the TLS setup.
- An independent review or penetration test before real customers use it.

## 6. Security gate (applies to every phase)

A phase is done only when:
1. All unit and API tests pass, including the authorization matrix for any new
   endpoint.
2. Linters and static analysis are clean (`ruff`, `mypy`, `bandit`, `tsc`,
   oxlint, `flutter analyze`).
3. Dependency, image and secret scans are clean or have a written exception.
4. The threat model is updated for what the phase added.
5. No new plain-HTTP path, no secret in git, no sensitive value in logs.
6. The user has reviewed and approved.

### 7.2 Database compatibility (Supabase and other databases)

Checked on 2026-10-25.

**Your current schema on newer PostgreSQL.** I ran `storely_cloud_schema.sql`,
every file in `supabase/migrations/`, a full second run (idempotency) and the
three SQL test files (`rls_test`, `sync_v2_test`, `device_codes_test`) on throwaway
containers. **All pass on PostgreSQL 18.6 and on 17.11.**

**Supabase.** Supabase's Postgres images are 17.11 and 15.19 on Docker Hub, and
self-hosted Supabase defaults to 17. I found no Supabase image or announcement
for PostgreSQL 18. So:
- Running our own server on 18 does not stop us going back to Supabase, because
  the schema also passes on 17. CI tests on both 17 and 18 to keep that true.
- Do not use any PostgreSQL 18-only feature (for example `uuidv7()`, virtual
  generated columns, async I/O settings) until we are sure we never need 17.

**What in the current schema is Supabase-specific** (counted in
`storely_cloud_schema.sql` and the migrations). The port replaces each one:

| Supabase-specific | Count | Replacement |
|---|---|---|
| `auth.uid()` | 24 | `app.uid()` reading `app.user_id` set per request |
| `auth.users` | 12 | our `users` table |
| `to authenticated` (role grants) | 10 | one application role, e.g. `storely_app` |
| `auth.jwt()` | 3 | removed; roles come from the database, not the token |
| `service_role` | 1 | a separate migration/admin role |

The only extension used is `pgcrypto`, which ships with PostgreSQL itself. No
`pg_cron`, `pg_net`, `vault`, storage or realtime objects are used.

**Other PostgreSQL hosts.** The schema uses only core PostgreSQL features (row
level security, PL/pgSQL, `jsonb`, `SECURITY DEFINER` functions, triggers,
`ON CONFLICT`, `timestamptz`), so it runs on any PostgreSQL host: AWS RDS and
Aurora, Azure, Google Cloud SQL, Neon, DigitalOcean, or a plain VPS. PostgreSQL
18 is generally available on AWS RDS (since November 2025) and Azure (December
2025). I could not confirm 18 on Google Cloud SQL, Neon or DigitalOcean, so
check the host's supported versions when we pick one in Phase 9. Running on 17
is the safe fallback.

**Other database engines (MySQL, SQL Server, SQLite).** Not compatible without
a rewrite. Row level security, PL/pgSQL triggers and `jsonb` are PostgreSQL
features, and the sync rules live in those triggers. "Database independent"
therefore means independent of *Supabase and any one host*, not of PostgreSQL.
I recommend keeping it that way; changing engine would mean rewriting the
security and sync logic for no customer benefit.

Decisions and caveats:
- Sync tables keep `double precision` money columns, exactly as the phone stores
  them, so rows round-trip unchanged. Reports will cast to `NUMERIC` and round to
  paise (Phase 7).
- A refresh retried within 10 s is accepted (a lost response must not log a
  shopkeeper out on a weak connection); replaying an older token revokes the
  session. This is a deliberate trade-off.
- Sign-in delay is per email, capped at 10 minutes, so an attacker who keeps
  retrying can keep a known address delayed (recorded as residual risk in T21).
- Mailpit's web UI was never reachable in Phase 0 (Docker cannot publish ports from
  an internal-only network); fixed by also attaching it to the edge network.
- Not yet built (belongs to later phases as planned): password reset and change,
  sessions list, two-factor, account deletion (Phase 2), shops and roles.

What was built and verified:
- **Account security:** password reset by emailed code (answers identically for every
  address, single use, signs every session out, clears a lockout); password change that
  keeps the current device and signs the rest out; list and revoke sessions; log out
  everywhere; append-only security-event log (the API role cannot edit or delete it,
  SQL-tested); alerts for new-device sign-in, password change and two-factor changes.
- **Two-factor (TOTP):** RFC 6238 test vectors pass; replay-proof; secret encrypted with
  AES-256-GCM bound to the user; ten one-time recovery codes stored as keyed hashes; a
  five-attempt challenge between password and code; turning it off needs password and a
  code. Optional switch `require_mfa_for_admins` (default off).
- **Shops and roles:** create (keeping the phone's own shop id), members, invites that
  match a verified email, device letters, change role (owner only), remove or leave,
  delete shop (owner, type the name). Roles are read from the database every request;
  a stranger gets the same 404 as for a shop that does not exist; Row Level Security is
  verified independently with raw SQL; identity never leaks across pooled connections.
- **Account lifecycle:** change email (code to the new address only, identical answer if
  taken, other devices signed out, old address told), data export (no secrets, rate
  limited), delete account (password and, if on, a second-factor code; refuses while the
  user owns a shop with other members; audit entry kept without a link to the account).
- **Authorization matrix:** every route must be declared with an access level, so adding
  a route without deciding who may call it fails the build; the public routes are an exact
  reviewed list; each role gets exactly the allowed outcome on every shop route.
- **Checks:** 14 unit tests, 88 integration tests, 4 SQL test files, strict typing, bandit,
  dependency audit, secret scan and image scan are clean; `make smoke` and `make verify`
  pass, including from a fresh clone. I broke 14 controls on purpose (session revocation,

  admin-invite rule, shared-shop deletion, password check on deletion, undeclared route,
  loosened owner rule and others) and each time the tests failed.

Decisions and caveats:

### Phase 3: Sync API (L)

**Status: DONE 2026-10-25.** `storelyapi` commits 439b70a (sync API, migration 0005) and
9923b45 (docs, smoke test).

What was built and verified:
- `POST /v1/shops/{shop}/sync/pull` and `.../sync/push`, matching the phone's `SyncBackend`
  (see `storelyapi/docs/API_CONTRACT.md` for how each `SyncBackend` method maps onto the API).
  Pull reuses the existing `sync_pull` function under the caller's identity and pages by
  `(server_updated_at, key)`. Push applies each row in its own savepoint and returns the
  refused rows by id, so one bad row never blocks the rest; resending is harmless.
- Conflict rules, tested at the API: latest edit wins whatever order uploads arrive in;
  an older deletion still applies; deleted bills, items, payments and stock movements stay
  deleted; staff cannot edit the catalogue or settings, cancel or change bills, issue
  credit notes or record non-sale stock movements; the audit log cannot be rewritten;
  the shop record is admin-managed.
- Safety beyond the old Supabase setup: every row must carry the URL's shop id; column names
  are checked against the table's real columns and validated as identifiers; values are
  bound parameters; refusal messages are fixed sentences (no database text); rows dated
  more than 24 h ahead are refused so a phone with a wrong clock cannot win every conflict;
  request bodies over 8 MiB get 413 (declared or chunked); sync is rate limited.
- A weakness found by a new test and fixed in migration 0005: a cancelled bill's status
  could be flipped back by an upload that simply left `deleted_at` out.
- Checks: 14 unit, 114 integration (26 for sync, including 2500-row paging past the old
  1000-row cap, ties on one timestamp, cross-shop attacks, two-phone convergence), 4 SQL
  test files, strict typing, bandit, audit, secret scan, image scan, `make smoke` and
  `make verify`; all pass, also from a fresh clone. Mutation-tested: the shop check, the
  clock guard and per-row isolation (one mutation first did not apply because the code
  was formatted differently; I redid it and confirmed the test fails).
- Timing (rough, in-process, local database, not a load test): pushing 2500 products in
  five requests and paging them back takes about 1.5 s.

Caveats and decisions:
- The plan said to run the Dart engine's scenarios against the real API. The Dart engine
  can only talk to a `SyncBackend`, which is the Phase 4 work, so for now the same
  scenarios are re-created as API tests. The real cross-check (the actual Dart
  `CloudSyncEngine` and `test/sync_engine_test.dart` against this server) is part of the
  Phase 4 gate.
- Staff can still pull `purchase_price` for products, as today. Hiding cost prices from staff
  is a web/API concern in Phase 6; the phone's staff view is unchanged.
- Soft-deleted rows are returned by pull on purpose, because the phone needs the deletion.
- Not done: a real load test (Phase 9) and any payload compression.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Billing logic duplicated (Dart and Python) | Shared test vectors; server authoritative for web bills; billing built last. |
| We own the security of billing data | Security gate on every phase, threat model, authorization matrix tests, independent review before launch. |
| Auth mistakes | Standard libraries, no custom crypto, token and brute-force tests, rate limiting from day one. |
| Sync regressions when changing the backend | Same protocol and triggers, contract tests against the fake, staged rollout. |
| Old 1.x installs still call Supabase | Keep Supabase alive until the new build has rolled out. |
| Report numbers differ between phone and web | Parity tests on a shared fixture dataset. |
| Local TLS setup friction on the Android emulator | Debug-only CA trust documented and tested in Phase 0/4. |
| Scope creep from "many things" on the backend | Only Phase 0-9 items; everything else waits in Phase 10. |

## 11. Working rules for all three repos

- Verify before you build (CLAUDE.md): investigate, report, wait for approval.
- Server schema changes go in Alembic migrations that are additive and safe to
  re-run. Never drop populated tables without a backfill plan. Flutter's local
  SQLite keeps its own additive migration pattern in `lib/db/database_schema.dart`.
  Until cutover, keep `supabase/migrations/` in sync for the legacy backend.
- Money is `Decimal` / `NUMERIC` on the server; round only at display.
- Keep `flutter analyze` clean; keep `ruff`, `mypy`, `bandit` and `pytest` green
  in `storelyapi`; keep `tsc`, oxlint and tests green in `storelyweb`.
- No secrets in git. The Flutter app ships only the API URL, never server keys.
- Do not change the Android bottom navigation or app flows without being asked.
